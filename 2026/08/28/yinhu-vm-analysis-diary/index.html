虚拟机里的银狐木马日记：从伪装驱动到代码完整性告警

发表于2026-08-28|更新于2026-08-28|网络安全协会暑期培训
|浏览量:

1. 这次分析从哪里开始

这篇文章记录一次并不顺利的样本分析。样本来自搜索下载的所谓“deepseek 电脑版”，我把它放进隔离虚拟机后，表面上几乎没有任何动作。没有明显窗口，没有稳定的网络行为，连预期中的安装流程也没有出现。起初我以为是样本损坏，后来结合静态分析和系统重启后的现象，才怀疑它把虚拟机环境当成了一个需要谨慎对待的目标。

本文只记录防御性分析结果，不复现木马的持久化、隐藏或破坏行为。所有实验都应该在可回滚的快照、断网或受控网络以及专用测试账户中进行。

2. 发现伪装成图片的驱动

样本释放出的一个关键文件名是 ranchserv.jpg。从扩展名看它像图片，但实际被当作驱动文件使用。仅凭扩展名判断文件类型很容易漏掉这类伪装，分析时应同时检查 PE 签名、文件属性、数字签名、服务配置和创建时间。

对这个驱动的派遣函数进行反编译后，可以看到它根据 IRP_MJ_DEVICE_CONTROL 的控制码分派不同功能。反编译器将控制码还原成了几组分支，其中比较值得关注的是：

  • 0x22E04C 附近的分支接收文件路径，调用内部函数打开文件并执行后续操作；
  • 0x22E048 附近的分支处理注册表键；
  • 0x22E014 附近的分支向内核结构中的成员写入数据；
  • 另有查询版本、复制数据和初始化结构的分支。

这些名称只是根据调用参数和上下文作出的分析性描述，不能替代对 sub_132A0、sub_13374 等内部函数的完整确认。不过，即使不掌握每个函数的精确语义，也能判断出风险边界：一个用户态客户端如果可以自由提交路径、注册表位置或内核地址，就可能借助该驱动修改系统状态，甚至破坏安全软件的加载条件。

特别是内核结构写入分支，不能简单当作普通配置接口。函数中存在将用户提供的数据写入结构成员的路径，实际目标可能是回调、列表或其他内核对象字段。这个结论需要通过符号、内存断点和调用栈进一步验证，但已经足够把驱动列为高风险样本，而不是普通的辅助驱动。

3. 为什么虚拟机里没有立即动作

样本入口附近存在一段环境初始化逻辑。它调用 GetSystemTimeAsFileTime、GetCurrentProcessId、GetCurrentThreadId、GetTickCount 和 QueryPerformanceCounter，组合出一个运行时值，同时保存其按位取反结果。这类代码本身更像安全 cookie 初始化，不能单独证明存在虚拟机检测。

在虚拟机中运行原始文件时，样本没有继续表现出明显行为。为了确认分支含义，我在隔离环境中对条件跳转进行了临时调试验证，观察到跳过退出分支后，程序才继续执行。这个结果说明 sub_14000113C 很可能参与环境检查或启动条件判断，但仍不能据此断言它只检查虚拟机，也可能综合判断调试器、系统版本、权限、网络或其他运行环境特征。

调试器附加后样本继续运行，也不能说明样本已经安全。相反，调试器本身可能改变时序、权限和系统观测结果，导致样本走到与普通启动不同的路径。后续实验应分别保留原始样本、调试副本和行为日志，不能把修改后的结果当作原始行为。

4. 一次代价很高的失误

确认启动分支后，我继续运行样本，却没有提前在关键位置设置足够的断点和行为监控。样本随后感染了虚拟机并自动重启。这个过程提醒我：逆向分析中“能跑起来”并不等于“值得继续跑”，尤其是涉及驱动、服务和系统策略的样本。

重启之后，虚拟机中的 SnowSword 驱动加载出现异常，用户态调用 ZwLoadDriver 返回 0xC0E90002。但在挂接 WinDbg 后，同一驱动又表现为可以加载。这个差异不能简单归结为“驱动文件时好时坏”，更合理的解释是系统启动时存在代码完整性策略拦截，而内核调试状态改变了策略处理结果。

5. 代码完整性日志给出的证据

在 Microsoft-Windows-CodeIntegrity/Operational 日志中，SnowSword.sys 对应了两类关键事件：

  • 事件 3077：代码完整性判断该驱动不满足 Authenticode 签名级别要求，或违反了当前代码完整性策略；
  • 事件 3004：系统无法验证映像完整性，提示找不到文件哈希，可能是签名错误、文件损坏或未知来源软件。

虚拟机中的 SiPolicy.p7b 时间戳晚于其他代码完整性文件，且日志持续指向策略违规。结合样本已经具备修改文件和注册表的高风险能力，可以提出一个较强的分析判断：系统代码完整性策略文件可能被样本篡改，或者至少被置于与干净系统不同的状态。不过，在没有同版本干净系统基线、文件哈希和签名链之前，仍应把它表述为“基于现有证据的疑似篡改”，而不是绝对结论。

6. 处置思路与证据保全

样本已经执行过驱动级动作并触发自动重启后，继续在原虚拟机中“修修补补”并不是优先选择。更稳妥的顺序是：

  1. 立即断开网络，保存虚拟磁盘、内存和事件日志副本；
  2. 记录服务项、驱动文件路径、文件哈希、创建时间和签名验证结果；
  3. 对 CodeIntegrity/Operational、System、Service Control Manager 和启动日志做时间线整理；
  4. 使用可信来源重新建立同版本系统快照，再对比 System32\CodeIntegrity 及 EFI 分区中的策略文件；
  5. 只有在证据已经保全后，才在副本上进行策略恢复和驱动加载验证。

如果需要恢复策略，应使用与目标系统版本和补丁级别匹配的可信基线，并先确认恢复操作不会破坏取证证据。EFI 分区中的副本也需要纳入检查范围；只替换系统目录中的单个文件，不能自动证明启动链已经恢复。恢复后应重新启动并复核代码完整性事件、策略状态和驱动签名，而不是只看一次 ZwLoadDriver 返回值。

7. 当前 IOC 与复核清单

目前能确认或需要重点复核的线索包括：

类型 线索
伪装驱动 ranchserv.jpg，实际按驱动用途加载
可疑样本 从搜索结果下载的所谓“deepseek 电脑版”安装包及其释放文件
可疑路径 C:\ProgramData\Oaxs10zK.exe、随机样式目录，以及样本实际落地路径
系统影响 自动重启、驱动服务被删除后再次出现、SnowSword 驱动加载异常
完整性日志 Code Integrity 事件 3004、3077
关键策略文件 System32\CodeIntegrity\SiPolicy.p7b 及 EFI 分区对应副本

上表中的路径和文件名来自本次环境记录，不能直接当作通用 IOC。实际处置时还应补充 SHA-256、签名证书链、服务注册表路径、父子进程关系和网络连接记录，并在多个时间点重复采集，避免把残留文件误当成当前活动组件。

8. 复盘：以后不会再忘记的几件事

这次样本给我的最大教训不是某个控制码，而是实验流程本身：

  • 在运行样本前先做快照，并准备第二份只读分析副本；
  • 先建立基线，再运行样本，至少记录驱动、服务、代码完整性策略和启动项；
  • 关键分支、服务创建、驱动加载和重启触发点必须提前布置观测手段；
  • 不把反编译器命名当成事实，所有高风险结论都要结合交叉引用、调用栈和系统日志；
  • “挂调试器后可以加载”只说明调试上下文改变了系统行为，不表示样本或驱动可信；
  • 对驱动级样本，恢复快照通常比在已感染系统中继续操作更可靠。

总结

从目前证据看，这个银狐样本至少表现出三条值得警惕的线索：使用图片扩展名伪装驱动、通过高权限接口修改文件/注册表/内核状态，以及根据运行环境决定是否继续执行。随后出现的自动重启和 SnowSword 驱动加载失败，则把样本行为与系统代码完整性问题联系到了一起。

但安全分析仍然需要克制。一次虚拟机实验可以提出假设，却不能替代完整取证；一次日志告警可以指出策略冲突，却不能单凭时间戳证明所有文件都由同一个样本修改。只有把静态分析、运行时观测、代码完整性日志、可信基线和快照前后差异放在同一条证据链上，才能更接近可靠结论。

这篇日记先记录到这里。下一步会在全新快照中补齐文件哈希、服务时间线和策略文件签名信息，并继续完善 SnowSword 对异常驱动和代码完整性事件的关联展示。
