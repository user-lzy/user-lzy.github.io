第十二篇日报：PyInstaller 样本逆向学习记录

1. 缘起：为什么值得单独写一篇 PyInstaller 样本分析

在 Windows 恶意样本里，Python 打包程序已经不算少见。攻击者把 Python 写的 loader、窃密器、键盘记录器用 PyInstaller 打成 exe，既能跨机器运行，又能把真正的逻辑藏进字节码里。对恶意样本分析师来说，把 PyInstaller 里的 Python 字节码完整提取出来往往是分析的第一步。

这次遇到的样本表面上是一个普通 Windows 程序：运行后提示 Enter input:，输入错误就输出 Wrong input。但用 IDA 打开后，入口逻辑并不是常见的 C/C++ 业务代码，而是 PyInstaller bootloader 的特征——它真正的逻辑在附加数据段里。更值得注意的是，这个样本对通用提取工具做了两处明显的对抗：

  1. PyInstaller 的 cookie 魔数被改写，导致 pyinstxtractor 直接报 “Missing cookie”；
  2. CArchive 里的 Python 模块数据被自定义加密，即使绕过 cookie 检查，解压也会失败。

这两处对抗单独看都不难，但组合起来正好可以整理出一条可复用的 PyInstaller 恶意样本静态提取方法链。

2. 先建立整体认知：PyInstaller 程序长什么样

PyInstaller 打包出来的 Windows 程序可以粗略分成两层：

关键点有两个：

  • cookie：一小段固定魔数，通常长这样：MEI\x0c\x0b\x0a\x0b\x0e。bootloader 从文件尾部往回搜索这段魔数，找到后解析后面的 CArchive 偏移和长度。
  • CArchive 条目：s 类型是入口脚本（如 main.py），m 类型是被 import 的模块，z 类型是 PYZ。它们大多数情况下是 zlib 压缩后的 Python marshal 数据。

通用提取器（如 pyinstxtractor）就是按这个结构工作的：先找 cookie，再读 TOC，再逐个解压条目。

6. 对恶意样本分析的启发

6.1 通用提取器失效时，方法链比工具重要

这次分析真正有价值的地方，不是“把 swI 改成 MEI”，而是面对失效时的思考顺序：

工具负责加速，但结构知识负责兜底。PyInstaller 的 cookie、TOC、条目类型、pyc 头这些都是公开且固定的，只要 bootloader 还在按这套结构运行，就能手工还原。

6.2 静态分析的边界

这个样本展示了静态分析的一个典型困境：字符串、魔数、数据头都可以被改写，甚至模块数据可以被整体加密。如果只依赖“搜字符串”和“跑通用提取器”，很容易得出错误结论。

但静态分析仍然有价值：bootloader 是原生代码，它必须实现解密逻辑，才能让 Python 运行时加载模块。只要找到 bootloader 里 inflate 之前的处理代码，就能还原整个数据变换。混淆可以藏数据，但藏不住处理数据的代码。

6.3 与 ARK / SnowSword 检测思维的关联

这个样本的对抗方式，和 Rootkit 隐藏自己的思路很像：

  • 恶意样本改掉 PyInstaller cookie 魔数 → 通用提取器失效；
  • Rootkit 摘掉 ActiveProcessLinks / 模块链表 → 通用枚举工具失效。

两者的共同点是：攻击者只需要让“单一数据源/单一工具”失效，就能显著提高分析门槛。 这也解释了为什么 SnowSword 做检测时要坚持多视角交叉验证——模块列表、对象目录、内存特征、运行时行为互相印证，而不是把某一个列表当成绝对事实。逆向分析同理：不能因为一个提取器报错就判定“不是 PyInstaller”，也不能因为一个字符串匹配就认定样本行为。

7. 遇到的问题与局限

  1. Python 版本不匹配：当前环境是 Python 3.11，样本是 Python 3.8，pyinstxtractor 对 PYZ 的自动提取会因 marshal 版本不匹配而跳过。主脚本在 CArchive 里不受影响，但 PYZ 内模块需要额外处理。
  2. 方法依赖具体 bootloader 修改：本次的 swdd + XOR 0xAA 是针对这个样本的定制逻辑；换一个样本，前缀、密钥、算法位置都可能变化，不能直接套脚本。
  3. 手工解析容易踩偏移坑：CArchive 的 TOC 条目是定长头 + 变长名字，解析时如果字段偏移算错，后面的条目会全部错位。写脚本时要先用已知 DLL 条目（能正常 zlib 解压）做自检。
  4. 反编译质量依赖工具：uncompyle6 对 Python 3.8 支持尚可，但遇到复杂控制流仍可能失败；必要时需要结合字节码 dis 手工分析。

这次分析形成了一条可以复用的 PyInstaller 恶意样本静态提取流水线：

后续可以把这套流程脚本化、半自动化：自动扫描 cookie 魔数变体、自动识别 swdd 这类前缀、自动尝试常见 XOR 密钥，并把 PYZ 内模块的提取也补全。再往后，还可以把同样的思路扩展到 PyArmor、Nuitka 等其它 Python 打包/加固方案，并尝试与动态行为分析结合，验证静态还原出的逻辑和实际运行行为是否一致。
