SnowSword--进程隐藏检测实现：从用户态枚举到内核对象分析

发表于2026-08-04|更新于2026-08-05|网络安全协会暑期培训
|浏览量:
项目地址：https://github.com/user-lzy/SnowSword

1. 为什么需要检测隐藏进程

在开发 SnowSword 之前，我曾使用过一些 ARK 类工具分析 Windows 系统。但在实际测试过程中发现，不同工具对于进程枚举结果可能存在差异。因此，我希望实现一种多视角交叉验证的方法，而不是依赖单一 API。

众所周知，部分恶意程序会通过 Hook R3 API（Process32Next、NtQuerySystemInformation）、Hook R0 API（ZwQuerySystemInformation）或篡改 R0 内核结构（EPROCESS 摘链、Hook ZwQuerySystemInformation）来隐藏进程，避免被用户通过系统自带的任务管理器等普通安全工具发现其活动。但正所谓”天网恢恢，疏而不漏”，我们可以使用一种交叉对比进程枚举结果的方法找出恶意程序的隐藏进程。

1.1 为什么需要多视角枚举？

Windows中不存在一个绝对可信的进程观察视角。

用户态工具、对象管理器、内核进程管理机制分别维护着不同的信息来源。
如果攻击者只修改其中一种视角，例如Hook某个用户态接口，
其他来源仍可能暴露异常。

因此，SnowSword的设计思路不是寻找一个万能的进程枚举接口，
而是从多个角度获取进程信息，并通过结果差异发现异常。

2. 不同视角下的进程枚举机制

2.1 用户态 API 枚举

  • Process32First + Process32Next：Windows 用户态最常见的进程枚举接口。但是它依赖用户态 API 调用链，如果攻击者 IAT Hook / Inline Hook 它或者更底层的数据来源，返回结果可能已经不可信。因此 SnowSword 中并不将其作为最终判断依据，而是作为一个”普通用户看到的世界”。

  • NtQuerySystemInformation(SystemProcessInformation, …)：Native API（由于不存在于导入库中，需要自行通过 GetModuleHandle + GetProcAddress 动态调用），可以获取更多进程信息，但由于它已十分出名，所以通常也会被列入 hook 名单。

2.2 内核态 API 枚举

  • ZwQuerySystemInformation(SystemProcessInformation, …)：内核最常见的进程枚举手段，获取的进程信息同 R3 的 NtQuerySystemInformation(SystemProcessInformation, ...)，但相较 R3 更可信。

3. SnowSword 实现方案

3.1 用户态获取进程列表

  1. 调用 Process32First + Process32Next 获取进程列表 a，作为进程列表基线用于交叉检测隐藏进程。

  2. 除了传统进程枚举 API 外，SnowSword 还尝试从系统句柄角度观察进程。Windows 中的进程对象通常会对应一个 Process 类型句柄，因此可以通过 SystemHandleInformation 获取全局句柄表，再筛选其中的 Process 和 Thread 类型。通过句柄反向获得 PID，形成进程列表 b。最后去重。

3.2 驱动获取进程列表

Windows 内核分配 PID 时采用 4 字节对齐的增量分配策略——PID 的高 30 位用于索引进程对象数组，低 2 位固定为 0。因此合法 PID 必然是 4 的倍数，以 4 为步长暴力枚举可以跳过 75% 的无效值。

具体实现：以 4 为步长暴力枚举 0 ~ 0x20000（131072）的 PID，尝试调用 PsLookupProcessByProcessId 获取进程对象指针，成功且 PsGetProcessExitStatus 返回值等于 STATUS_PENDING（为了排除部分僵尸进程）则将 PID 插入进程列表 c。

该方法本质上利用了系统 PID 管理机制进行间接验证，与直接遍历 PspCidTable 相比实现简单，但效率和兼容性存在限制。

最初考虑过直接遍历 EPROCESS 链表，但是该方案存在两个问题：

  1. 不同 Windows 版本结构变化较大。
  2. 如果攻击者采用 DKOM 隐藏，同样可能影响该链表。

因此 SnowSword 选择通过 PID 反查方式，利用系统自身 PID 管理机制获取进程对象。虽然扫描范围有限，但不依赖固定结构偏移。

3.3 用户态与内核态结果比较

比较进程列表 a、b、c，在 UI 中标记出现在列表 b/c 但未出现在列表 a 的隐藏进程。

3.4 隐藏进程检测实验

实验结果：

工具 是否看到 TestAPI.exe 原因

这就验证了单一 R3 API Hook 无法对抗多视角交叉检测的观点。

在驱动层枚举时，我们通过 PsGetProcessExitStatus 过滤掉 STATUS_PENDING 以外的进程，避免将已退出进程误判为隐藏进程。而用户态的 Process32Next 通常不会返回这些已退出进程，这也解释了为什么 SnowSword 的进程列表比任务管理器”更长”——它包含了更多内核视角的信息。

4. 开发过程中遇到的问题

4.1 比较结果

一开始我想当然以为直接取列表 a 和列表 b/c 的差集即可，但 UI 上会出现重复显示的隐藏进程，排查后才发现是因为一个进程可能：被多个进程打开句柄，或是拥有多个线程句柄。所以 Handle-PID 不是简单的一对一关系，需要使用 HashSet 保存 PID。

4.2 僵尸进程判断问题

测试过程中发现，部分已经退出的进程对象仍然可能短时间存在。因此不能简单认为 PsLookupProcessByProcessId 成功即可，需要结合 PsGetProcessExitStatus 进一步判断。

5. 后续优化方向

目前 SnowSword 的隐藏进程检测仍存在限制：

  1. PID 扫描范围固定
  2. 依赖 PsLookupProcessByProcessId
  3. 无法发现所有内核级隐藏方式

后续计划：

  • 解析 PspCidTable 的三级表结构获取进程列表
  • 增加线程交叉验证
